# Astera 商品、訂單與購物車介面設計

**日期：** 2026-08-12  
**狀態：** 已完成視覺確認，待使用者檢閱本書面規格  
**關聯：** 延伸 `2026-08-12-home-states-design.md` 與 `2026-08-12-commerce-navigation-design.md`，其共用 Header 規格以本文件補充為準

## 1. 目標與範圍

將既有商品、商品詳情、購物車、Checkout 入口、訂單詳情與付款回報入口改為一致的 Astera 收藏選物店介面。會員能快速找到下一步，公開訪客仍能瀏覽公開商品，但不會繞過既有 Google 登入、Profile 完整性或 Server 驗證。

本次只改現有頁面與共用元件的顯示、導覽及既有連結：`/products`、`/products/[id]`、`/cart`、`/checkout`、`/orders`、`/orders/[id]`、`/payments` 及共用 Header／購物車抽屜。不得建立平行展示頁、改 Collection、修改 Firestore Rules、改變 Campaign 價格、Checkout 拆單、付款、取消或退款商業邏輯。

## 2. 共用 Header 與手機導覽

桌面 Header 維持白底、細邊框、左側 ASTERA 襯線 Logo。公開狀態右側為商品、品牌、常見問題、會員登入與購物車；登入後為購物車、我的訂單與帳號控制。Owner 的帳號控制區加上僅由 Firebase custom claim 決定的「管理後台」入口。

手機 Header 固定保留三個項目：ASTERA、購物車、選單按鈕。點選選單後，導覽在 Header **下方垂直展開**，不是側邊抽屜：

- 未登入：商品、品牌、常見問題、使用 Google 登入。
- 已登入：您好，會員名稱、我的訂單、我的帳號、商品、品牌、常見問題、登出。
- Owner：在已登入項目最上方額外顯示管理後台。

選單項目皆至少 44px 高；開啟後可由同一按鈕、Esc、點擊導覽項目或路由切換關閉。焦點順序與視覺順序一致，並遵守既有 `prefers-reduced-motion`。購物車保持固定可見，避免會員需先展開選單才能查看高頻購買操作。

## 3. 商品列表

商品列表只讀 `productsPublic`。手機固定 2 欄、768px 維持 2 欄、1365px 為 4 欄；不允許水平溢出。每張卡使用固定 4:5 圖片比例，圖片為主視覺，並只保留：

1. 藝人／系列。
2. 商品名稱。
3. 起始或有效售價。
4. Sale Type。
5. 結單時間與文字倒數。
6. 明確的二補 Badge（只有適用時）。

商品名稱、圖片均可進詳情；加入購物車按鈕至少 44×44px。公開商品的 Loading 用固定比例 skeleton，Empty 用消費者語句，Error 顯示中文原因與重試。不得顯示 SKU、成本、內部備註、Firestore、projection 或開發文字。

## 4. 商品詳情

桌面採左側商品圖、右側採購資訊；手機改為上圖下資訊。手機圖片為左右滑動相簿，保留 4:5 比例與可辨識的目前位置提示；不在首屏加入縮圖列。首屏資訊依序為：藝人／系列、商品名稱、價格、結單時間與倒數、二補標示、規格選擇、加入購物車。

活動說明、完整商品描述、補充規則與購買注意事項移到首屏下方。訪客按加入購物車時遵守現有登入意圖保存與 Google 登入流程；登入後仍先走既有必要 Profile 導向，再由 Server／權威商品資料驗證加入。

## 5. 購物車抽屜與完整結帳

Header 購物車按鈕顯示目前數量。點擊後從**右側**開啟迷你購物車抽屜：顯示品項、規格、數量、小計與總額，並提供 `查看購物車` 與主要按鈕 `前往結帳`。

抽屜使用淡化背景，並可由關閉按鈕、Overlay、Esc 或路由切換關閉。它是可存取的 labelled dialog，控制項至少 44px，過場遵守 reduced-motion。抽屜只讀既有匿名／會員購物車；數量修改與移除仍在 `/cart`，避免複製寫入邏輯。

`前往結帳` 進入既有 `/cart`／`/checkout` 連續流程。完整頁面才顯示收件資料、唯一的 7-ELEVEN 賣貨便配送方式與下單／二補同意；建立訂單及其後付款回報仍完全沿用既有受保護 API 與 Server 驗證。

## 6. 訂單與付款回報

訂單列表與訂單詳情首屏永遠保留一張狀態卡。待付款或需要會員補件時，卡片呈現清楚的下一步主行動，例如 `前往付款回報`；付款已確認、待出貨或完成等沒有會員待辦的狀態，卡片改以低干擾摘要顯示：`目前無需處理` 與當前狀態文字。

卡片後方才是商品、金額、配送與歷程內容。如此每一筆訂單都以相同閱讀順序呈現，會員一開啟即可辨識是否需要行動。

`前往付款回報` 連到既有 `/payments`，並只預選該會員可用的待付款請求。Server 必須繼續驗證 Payment Request 所屬會員；付款頁也保留既有多筆可選請求與一筆匯款分配多筆訂單的能力，不會由 UI 信任前端金額或請求 ID。

## 7. 視覺與無障礙要求

沿用既定 Token：Page `#F7F3F2`、Surface `#FFFFFF`、Ink `#20242B`、Border `#DED7D6`、Secondary `#6C6B70`、Brand `#6E4E64`、Brand Soft `#E7DDDF`、Service `#466060`、Campaign `#F8C7CC`、Catalog `#81A684`。

公開前台維持暖白、留白充足、細邊框與安靜的收藏選物店語氣；避免深色 Dashboard 卡、大量主色、Emoji 或 OMS／技術文案。控制項有 hover、pressed、disabled 與 `:focus-visible` 狀態；非同步行動需禁用重複提交並告知處理中；成功／一般狀態使用 `aria-live`，錯誤用 `role=alert`。圖片必須使用既有公開來源與尺寸保留策略，避免 CLS。

## 8. 驗收

- 390px：手機 Header 不溢出、選單由下展開、商品列表 2 欄、詳情相簿可操作、所有主要目標至少 44px。
- 768px：卡片、表單與抽屜沒有重疊或水平捲動。
- 1365px：商品列表 4 欄，詳情保持左圖右資訊，購物車抽屜不遮斷鍵盤操作。
- 訪客仍可瀏覽公開資料；商品加入與結帳相關受既有登入／Profile 規則約束。
- 狀態卡對待付款訂單會前往正確會員所有的付款請求；無待辦訂單顯示低干擾摘要。
- Owner 可見管理後台，Member／Helper 不會因 UI 而取得 Owner 權限。
- 測試涵蓋 TypeScript、ESLint、Unit、Build、公開 Playwright 及相關認證 Emulator Playwright。

## 9. 明確不做

- 不更動 `productsPublic`、`productsInternal`、Collection、Firestore Rules、價格、Campaign、Checkout 拆單、付款、取消或退款資料模型。
- 不建立假商品、外部示意圖片、平行首頁或展示專用流程。
- 不把付款或訂單私密資料放在公開 Header、公開商品頁或未登入狀態。
