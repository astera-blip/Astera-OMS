# 會員匯款帳戶與匯款人連動設計

**日期：** 2026-08-11
**狀態：** 已確認並完成本地實作
**範圍：** 會員匯款帳戶綁定、既有帳戶補填、付款回報帳戶選擇與付款快照

## 1. 需求與既有規格關係

本設計延伸 `2026-08-03-member-bank-account-refund-design.md`，不改變其 HMAC、完整帳號資料最小化、五筆帳戶上限、刪除申請、退款比對與 14 天加密暫存規則。

新增的正式需求如下：

- 會員綁定每一筆銀行帳戶時，必須同時輸入該帳戶的匯款人姓名。
- 付款回報只能選擇會員自己的可用帳戶。
- 選擇帳戶後，帳號末五碼與匯款人姓名由帳戶資料自動帶入，不得在付款回報頁手動修改。
- 會員有多筆可用帳戶時，以單一選單選擇；只有一筆時仍使用相同選單並預設選取。
- 既有帳戶若缺少匯款人姓名，帳戶保留但不得用於新的付款回報；會員可補填一次姓名後恢復使用，不必重新輸入完整帳號或重建 HMAC。

本設計以新增 `payerName` 延伸 `memberPaymentAccounts`。完整會員銀行帳號仍不得永久保存。

## 2. 方案比較與決策

### 方案 A（採用）：姓名隸屬每筆會員帳戶

每筆帳戶保存自己的匯款人姓名。此方案能處理同一會員不同帳戶使用不同匯款人姓名，並讓付款快照忠實反映實際來源帳戶。

### 方案 B：一律使用會員 Profile 姓名

資料較少，但會員姓名不一定等於實際銀行匯款人，可能增加人工對帳錯誤。

### 方案 C：每次付款回報手動輸入

彈性最高，但容易輸入不一致，無法達成帳戶與匯款人連動。

採用方案 A。

## 3. 資料契約

### `memberPaymentAccounts`

在既有正式欄位上新增：

- `payerName`：會員綁定該帳戶時提供的匯款人姓名。

永久帳戶資料仍只保存：

- `memberId`
- `bankCode`
- `accountNumberLast5`
- `accountFingerprint`
- `fingerprintAlgorithm`
- `fingerprintKeyVersion`
- `payerName`
- `status`、`verificationStatus`、時間與既有審核欄位

禁止保存 `accountNumberFull`。完整帳號只在建立請求中短暫存在，完成正規化、末五碼擷取與 HMAC 運算後立即丟棄。

### Payment 的會員帳戶快照

付款建立時，Server 根據 `memberPaymentAccountId` 重新讀取帳戶並保存快照：

- `bankCode`
- `accountNumberLast5`
- `accountFingerprint`
- `fingerprintAlgorithm`
- `fingerprintKeyVersion`
- `payerName`

付款快照建立後不可因帳戶資料變更而回寫，確保歷史對帳可稽核。

## 4. UI 與流程

### 綁定新帳戶

會員帳戶表單包含：

1. 銀行代碼。
2. 完整銀行帳號。
3. 匯款人姓名。

送出時只傳給受保護 API。成功後，UI 清除完整帳號輸入，只顯示銀行代碼、遮罩帳號、匯款人姓名與帳戶狀態。

### 既有帳戶補填

- 缺少 `payerName` 的既有帳戶顯示「需要補填匯款人」。
- 補填前不出現在付款回報的可用帳戶選單。
- 會員可從帳戶管理頁進行一次補填；請求只接受匯款人姓名，不要求完整帳號，也不得修改銀行代碼、末五碼或 HMAC 欄位。
- 補填成功後，帳戶恢復為可供付款回報選擇。
- 歷史 Payment 快照不回寫。

### 付款回報

- 表單只使用一個「匯出匯款的會員帳戶」選單。
- 選項格式：`銀行代碼 012・***12345・王小明`。
- 選擇帳戶後，另以唯讀欄位顯示帳號末五碼與匯款人姓名。
- 前端送出 `memberPaymentAccountId`、付款請求、日期、金額、收款帳戶與備註；不送出可作為權威資料的末五碼或匯款人姓名。
- 沒有可用帳戶時，不得送出付款回報，並提供前往帳戶管理頁的明確連結。

## 5. Server 驗證與權限

- 建立新帳戶時，`payerName` 為必填；去除前後空白後長度為 1～80 個 Unicode 字元。
- 拒絕空白姓名、控制字元與換行；保留合法中英文、空格、中點及一般姓名標點。
- 補填 API 只允許帳戶擁有者操作自己的既有帳戶，且只允許在 `payerName` 缺失時寫入一次。
- 補填 API 不得修改銀行代碼、末五碼、指紋、金鑰版本、帳戶擁有者或歷史 Payment。
- 付款 API 不信任 Client 提供的末五碼或匯款人姓名；即使 Client 偽造這些欄位，也只能使用 Server 重新讀取的帳戶資料建立快照。
- 付款 API 驗證帳戶屬於目前會員、狀態可用、驗證狀態有效且 `payerName` 完整。
- Client SDK 繼續禁止直接讀寫 `memberPaymentAccounts` 與 Payment 業務資料。
- Owner 與 Helper 權限邊界沿用現有 custom claim 規格，不以 Email 判斷。

## 6. 錯誤處理

- 新帳戶缺少或不符合格式的匯款人姓名：拒絕建立並顯示欄位中文錯誤。
- 舊帳戶缺少姓名：保留帳戶，標示需要補填，不視為資料讀取失敗。
- 補填重複送出：若姓名已存在則拒絕覆寫，回傳不洩漏帳戶資料的中文錯誤。
- 選定帳戶在送出前被封存、進入刪除流程或變為不可用：Payment 不建立，要求會員重新選擇。
- Payment 建立失敗不得以 localStorage 或前端資料偽裝成功。

## 7. 測試與驗收

### Unit／API

- 新帳戶必須包含合法 `payerName`。
- 姓名正規化、長度與控制字元驗證。
- Firestore write 與 API response 不包含完整帳號。
- Public account snapshot 包含匯款人姓名，但不包含完整帳號或 HMAC 輸入。
- 缺少姓名的舊帳戶仍可讀取但不可用於付款。
- 帳戶擁有者可補填一次；第二次覆寫、跨會員與其他欄位修改均拒絕。
- Payment API 忽略或拒絕 Client 偽造的末五碼與姓名，並保存 Server 權威快照。

### Firestore Rules

- Member、Helper、Owner Client SDK 均不可直接讀寫會員付款帳戶的私有業務文件。
- 跨會員帳戶與付款資料維持拒絕。

### Playwright／真人 Preview

- 建立兩筆不同末五碼及匯款人姓名的測試專用帳戶。
- 付款回報選單切換帳戶後，唯讀末五碼與匯款人同步切換。
- 只有一筆可用帳戶時自動選取並顯示連動資料。
- 舊帳戶補填前不出現在選單，補填後可選。
- 送出後建立單一 `pendingReview` Payment，其會員帳戶快照與選定帳戶一致。
- 重新整理頁面後仍不顯示或回傳完整銀行帳號。

## 8. 完成條件

- 新增及既有帳戶流程均具備正確的匯款人姓名。
- 多帳戶以單一選單操作，末五碼及匯款人只由選定帳戶衍生並唯讀顯示。
- Server 是付款帳戶快照的唯一權威來源。
- 完整銀行帳號仍不永久保存、不進日誌、通知、URL、前端持久化或 API response。
- 歷史 Payment 不回寫。
- Unit、API、Rules、Playwright、TypeScript、ESLint、Build 與 Preview 真人驗收通過。

## 9. 明確不在本次範圍

- 不允許會員一般編輯既有銀行代碼、末五碼、完整帳號或匯款人姓名。
- 不修改五筆上限與刪除申請流程。
- 不修改 HMAC／Cloud KMS／退款帳號 14 天加密暫存設計。
- 不新增 Finance、Wallet、CRM 或其他 ERP 功能。
